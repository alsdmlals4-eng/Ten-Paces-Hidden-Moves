## Practical architecture and inspected failure path

[Godot Dictionary documentation](https://docs.godotengine.org/en/stable/classes/class_dictionary.html) confirms unique keys, reference semantics, and that duplicate(true) recursively copies nested arrays/dictionaries but not Resources. ADOPT two owned Dictionary snapshots and copied return values for JSON-shaped definitions; REJECT a per-actor duplicate catalog or renamed content IDs. No new dependency, threading or engine upgrade is needed.

Actual `combat_resolution_engine_ten_manuals.gd` registers player cards then enemy cards into shared `cards_by_id`; equal IDs overwrite even when mastery differs. `resolve_martial_card` and `_run_martial_pipeline` re-read that shared map. Separate ID membership sets do not prevent an incorrect star5/star9 overlay. `_build_enemy_actions`, `CombatResolutionEnginePrepare._enemy_attempts_from_result`, the bridge's checkpoint export and combat codec must resolve against the same actor-owned definition. The UI adapter independently composes the player's registry definition, so an apparently correct label can disagree with execution or be rejected by checkpoint validation.

Actual `martial_effect_pipeline.gd` reads SPECIAL_CLASH `stat` strings directly from actor.stats. Eight current steps use Korean names while actual combat actor state uses external/constitution/agility/internal_power/insight. Example: Nangong star3 declares8 + 내공×1; internal_power4 currently reads as8, not12. Existing standalone pipeline fixtures use Korean-only actor keys and conceal this mismatch. The approved effect coefficients and stats already own the intended meaning; no price or power rebalance is required.
