## Current engine and practical feasibility

- [Godot saving games](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html): explicit persistent fields and JSON limitations. ADAPT a small explicit data contract, not whole-Node serialization.
- [FileAccess](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html): user data writes, flush/close and error inspection. ADOPT checking every storage operation.
- [DirAccess](https://docs.godotengine.org/en/stable/classes/class_diraccess.html): rename returns an Error; existing destinations may be overwritten unless protected. ADAPT temp validation followed by replacement and a good backup. This is not proof of power-loss durability on every filesystem.

FEASIBLE on current Godot 4.7.1: `vertical_slice_run_state.gd` owns route/reward/retry transitions; `vertical_slice_progression_state.gd` already exposes a snapshot but its permissive restore is not an external-input validator. `combat_board_preview.gd` resolves the complete bundle synchronously before animating intermediate states. `combat_resolution_engine.gd` keeps the enemy lock outside combat_state; that lock must also persist. Shell scene uses completion -> route -> result -> base inheritance, and route shell reapplies resources in its combat-view hook. A restore must occur after new-view configuration, never before that overwrite.
