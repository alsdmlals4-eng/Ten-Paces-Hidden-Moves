# 십보강호 구현 로드맵과 검증 기준

> 책임: 현재 작업·PoC·T1·구현·검증 진입 순서

## 1. 현재 단계

```yaml
phase: PLANNING_IN_PROGRESS
project_core: CORE_CONFIRMED
implemented_runtime: IMPLEMENTED_LEGACY
new_poc_planning: AUTHORED_NOT_IMPLEMENTED
human_step14: NOT_RUN
t1_greenlight: NOT_GRANTED
```

## 2. 현재 작업

- [x] 구형 규칙과 활성 소비자 감사.
- [x] 1~10 PoC 기획 데이터를 편집 가능한 JSON으로 작성.
- [x] 전투·콘텐츠·성장·지도·UI·QA 책임 원본 동기화.
- [x] 벤치마킹·1·2차 기획 검수·5회 적대적 검토.
- [ ] 사용자 기획 검토와 명시적 `기획 완료`.
- [ ] 검수 루프와 명시적 `검수 완료`.
- [ ] Codex 구현 인계.

## 3. 프로젝트 코어 확정

1대1·10칸·비공개 3/3/4·공개 정보 기반 상대 읽기·거리·합·대응·중단·복기는 불변이다. 로그라이트 성장은 다음 결투 판단을 바꾸는 보조 구조다.

## 4. P0 — 편집 데이터와 계약 구현

기획·검수 완료 뒤 Codex가 수행한다.

1. planning JSON을 런타임 Schema로 변환하는 명시적 adapter.
2. 속공4·강공10·방어도5·내력5·명상1/1·`[강화]`·새 `[강건]`.
3. 순차 연격 `[합]`, 중단, 잔여타, 효과 scope/trigger.
4. 결과 이벤트·로그·복기.
5. 정상·실패·경계·회귀 테스트.

## 5. P1 — 다음 PoC

- 주요 비무 1~3.
- 시작 무공 6개 중 4개 선택.
- 전투 사이 성장 선택 2회.
- 총 방문 노드 5.
- 목표 플레이 시간 25~40분 가설.

성공하면 `KEEP / AMPLIFY`, 규칙 이해는 되나 재미·선택이 약하면 `CHANGE / RETEST`, 이해가 막히면 `REMOVE / REPEAT_POC`로 판정한다.

## 6. STEP 14

- 신규 플레이어 5명.
- 4명 이상 치명적 차단 없이 완료.
- 4명 이상 3/3/4와 결정적 원인을 설명.
- 3명 이상 상대 성향 발견.
- 3명 이상 재도전에서 계획 변경.
- 색·모션·음향 단일 채널 의존 없음.

현재 STEP 14는 `NOT_RUN`이다.

## 7. T1 — 최소 세로 슬라이스

PoC 사람 증거와 제작 반복성 증거 뒤에만 진입한다. 대표 경험·목표 품질·접근성·성능·파이프라인을 한 구간에서 검증하며 전체 10비무를 만들지 않는다.

## 8. 공통 검증 게이트

```text
계약·Schema
→ JSON·정적 검사
→ 자동 테스트
→ Godot runtime
→ Windows·접근성·성능
→ 사람 플레이
→ 증거 보고
```

실행하지 않은 단계는 `NOT_RUN`이다.

## 9. 중단·축소 조건

- 연격이 다른 공격을 지배한다.
- 성장 선택이 피해 증가만 만든다.
- 공개 성향 없이 정답 추측에 의존한다.
- 3/3/4가 이해되지 않는다.
- 두 번째 무공·적을 같은 데이터 구조로 만들 수 없다.
- 플레이어 미확정 계획을 AI가 읽는다.

판정 어휘: `KEEP / AMPLIFY / CHANGE / REMOVE / DEFER / RETEST`.
