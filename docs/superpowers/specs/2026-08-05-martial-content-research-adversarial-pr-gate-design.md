# 무공 콘텐츠 사전 조사·적대적 검토·PR 게이트 설계

## 상태

```yaml
status: USER_APPROVED_PROCESS_AWAITING_WRITTEN_SPEC_REVIEW
approved_at: 2026-08-05
approval_batch: 4/10
implementation_authority: PLANNING_ONLY
product_runtime_changed: false
proposed_decision_id: TEN-DEC-20260805-MARTIAL-CONTENT-RESEARCH-ADVERSARIAL-PR-GATE-01
```

## 목적

앞으로 무공서·기술·9성 완성 효과·10성 절초를 추가하거나 수정할 때, 아이디어나 예산 계산부터 시작하지 않는다.

반드시 다음 게이트를 순서대로 통과한다.

```text
사전 조사
→ 프로젝트 정본·진행 상태 파악
→ 무학·기술 방향 설계
→ 적대적 검토 루프
→ PR 계보·충돌·리뷰 상태 확인
→ 사용자 승인
→ TDD 구현·정본 동기화
→ exact-head 검증
```

## 적용 범위

이 게이트는 다음 작업에 항상 적용한다.

- 신규 무공서 추가
- 기존 무공서의 무학·방향성 변경
- 기술1·5성 효과 추가 또는 변경
- 기술2·9성 효과 추가 또는 변경
- 10성 절초 추가 또는 변경
- 무공 이름·기술 이름·설명·해결 순서 변경
- 슬롯·비용·조건·거리·이동·합·회피·방어·회복 수치 변경
- 무공 관련 정본·카탈로그·런타임 데이터 변경

단순 오탈자 수정은 의미·규칙·수치가 바뀌지 않는다는 검증 후 축약 절차를 사용할 수 있지만, PR 상태 확인은 생략하지 않는다.

# 1. 사전 조사 게이트

## 1.1 내부 정본 조사

작업 전에 최소 다음을 확인한다.

- 현재 권위 Decision과 overlay 계약
- Game Design·Combat Rules·Mastery·Technique Catalog
- Active Context·Roadmap·Lifecycle Registry
- 연결된 Google Sheet의 현재 결정·작업 순서·변경 이력
- 관련 기술1·기술2·9성·절초의 기존 역할과 예산
- 현재 브랜치·Draft PR·stacked PR 계보
- 같은 파일·Decision 영역을 수정하는 병렬 PR

내부 정본을 읽지 않고 기억이나 과거 대화만으로 무공을 설계하지 않는다.

## 1.2 외부·현업 조사

각 무공의 방향성에 맞춰 필요한 근거를 먼저 조사한다.

조사 대상 예시:

- 실제 무술·병장기 운용 원리
- 무협 장르의 일반적인 무학 표현과 명명 관습
- 전술 게임의 거리·방어·반격·회피·자원 설계 사례
- 복합 기술의 해결 순서와 가독성 사례
- 유사 기술의 밸런스 실패·악용·무한 루프 사례

조사 원칙:

- 공식·1차·전문 자료를 우선한다.
- 게임·소설 사례는 구조만 벤치마킹하고 표현·이름·효과를 복제하지 않는다.
- 출처와 채택·기각 이유를 조사 기록에 남긴다.
- 사실 검증이 필요한 내용은 웹 검색으로 확인한다.
- 조사 결과가 프로젝트 코어와 충돌하면 외부 사례보다 프로젝트 코어를 우선하고 충돌을 기록한다.

## 1.3 조사 산출물

설계 전에 짧은 Research Brief를 남긴다.

```text
조사 목적
내부 정본 근거
외부 벤치마크·출처
채택할 원리
기각할 원리
프로젝트에 맞게 변형한 점
남은 불확실성
```

근거 없는 "멋있어 보이는 효과"만으로 다음 단계에 진입할 수 없다.

# 2. 무학·기술 설계 게이트

사전 조사 뒤 다음 순서로 설계한다.

```text
1. 무공서 방향성·무학
2. 기술1·기술2·9성·절초의 역할과 성장 관계
3. 각 기술의 해결 순서
4. 실패 조건·상대 대응·금지선
5. 효과 구성
6. 예산 편성
```

예산은 무학을 정하는 도구가 아니라, 확정한 무학을 과도하지 않게 구현하는 제약 장치다.

# 3. 적대적 검토 루프

## 3.1 필수 공격 관점

각 설계안을 최소 다음 관점으로 공격한다.

### 정체성 공격

- 다른 무공의 기술로 바꿔도 차이가 없는가.
- 무학 설명과 실제 효과가 연결되지 않는가.
- 피해·방어 수치만 바꾼 동형 기술인가.

### 역할 중복 공격

- 기술2가 기술1을 전 상황에서 폐기하는가.
- 절초가 하위 기술의 단순 합산·상위호환인가.
- 다른 무공의 핵심 역할을 침범하는가.

### 해결 순서 공격

- 후퇴가 반격 사거리를 끊는 등 스스로 효과를 방해하는가.
- 상태 생성·기록·판정·소비 순서가 모호한가.
- 동일 사건을 두 번 계산하거나 결과에 따라 소급 재계산하는가.

### 상대 대응 공격

- 거리·합·회피·중단·자원 부족 실패를 자동 삭제하는가.
- 숨은 계획·AI 가중치·정답 행동에 접근하는가.
- 자동 필중·무적·무제한 반격으로 변하는가.

### 예산·악용 공격

- 조건 보상을 받으면서 기술 자체가 조건을 생성하는가.
- 방어·회복·피해가 서로 재귀해 무한 성장하는가.
- 최대치·상한·스냅샷 시점이 없어 폭주하는가.
- 실패 보상을 이용해 고의 실패가 최적이 되는가.

### UX·가독성 공격

- 카드 한 장에서 해결 순서를 이해할 수 있는가.
- 추가 입력·버튼·선택 때문에 커밋된 행동 묶음이 멈추는가.
- 같은 용어가 다른 기술에서 다른 뜻으로 쓰이는가.

### 이름·출처 공격

- 실제 고유 문파·작품·상표를 불필요하게 모방하는가.
- 이름과 동작이 어울리지 않는가.
- 한자식 이름이 의미 없이 장식적으로만 붙었는가.

## 3.2 루프 절차

```text
초안
→ 공격 목록 작성
→ P0/P1/P2 등급화
→ 수정안 작성
→ 반대 관점에서 재공격
→ 남은 위험과 사람 검증 항목 기록
```

- P0: 정본 충돌·무한 루프·자동 정답·런타임 불능. 해결 전 승인 금지.
- P1: 역할 대체·예산 폭주·순서 결함·핵심 UX 혼란. 해결 전 구현 금지.
- P2: 이름·설명·미세 밸런스·사람 검증 필요. 위험 기록 후 승인 가능.

검토 결과는 "문제 없음" 한 줄로 끝내지 않고, 공격한 가설과 수정 근거를 남긴다.

# 4. PR 체크 게이트

무공 설계를 확정하거나 파일을 쓰기 전에 반드시 현재 PR 상태를 확인한다.

## 4.1 필수 확인 항목

- 작업 대상 저장소와 정확한 브랜치
- 활성 Draft PR 번호·head SHA·base SHA
- stacked PR 부모·자식 순서
- mergeable 여부
- merged·closed·superseded 여부
- 관련 파일을 수정하는 다른 활성 PR
- 같은 Decision ID·다음 Decision을 소유하는 PR
- unresolved review thread
- 요청 변경·실패 CI·보류 사유
- 최신 head가 Google Sheet와 일치하는지 여부

## 4.2 충돌 처리

다음 중 하나라도 있으면 구현을 멈추고 충돌 해결안을 먼저 만든다.

- 병렬 PR이 같은 권위 문서·계약·Sheet 범위를 수정
- 현재 브랜치가 승인된 부모 head를 포함하지 않음
- Active Context·Roadmap의 PR 계보가 GitHub 실제 상태와 다름
- 이미 superseded된 PR이나 Decision을 현재 권위로 사용
- unresolved P0/P1 리뷰가 존재
- CI가 설계와 무관한 이유가 아니라 실제 계약 위반으로 실패

PR을 병합하거나 닫는 행위는 사용자 명시 승인 없이 수행하지 않는다.

# 5. 사용자 승인 게이트

다음은 반드시 사용자 승인 대상이다.

- 무공서 방향성·무학 변경
- 기술 역할·해결 순서 변경
- 기존 확정 효과 제거·대체
- 기술1·기술2·절초 역할 충돌의 선택
- 예산 공식이나 중앙 가격 변경
- 프로젝트 코어와 외부 벤치마크가 충돌하는 선택

세부 수치가 기존 공식 안에서 계산되는 경우 권장안을 제시할 수 있지만, 기획 충돌은 GrillMe 질문으로 승인받는다.

# 6. 구현·검증 게이트

승인 뒤에도 바로 정본을 수정하지 않는다.

```text
RED 테스트·계약 검사
→ RED 증거 커밋
→ GREEN 최소 구현
→ REFACTOR
→ exact-head 전체 검증
→ PR 상태·리뷰 재확인
→ GitHub·Google Sheet 동일 Decision ID 동기화
```

필수 검증:

- 무학·역할·해결 순서 필드 존재
- 예산 원가·허용 편차 계산
- 조건 자체 생성과 조건 할인 중복 금지
- 기술1·기술2·절초 역할 비대체
- 자동 정답·숨은 계획 접근 금지
- 카드·카탈로그에서 실행 순서 가독성
- 신규 Decision·문서·계약·Sheet의 동일 ID·exact SHA

제품 코드·Godot·HTML·런타임 데이터를 변경하지 않은 경우 이를 명시하고 runtime 검증은 `NOT_RUN`으로 남긴다.
