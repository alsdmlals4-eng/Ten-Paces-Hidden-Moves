## 1. 승인 배치

- 한 승인 배치는 서로 구분되는 사용자 승인 Decision 최대 `10건`이다.
- 10건을 넘는 작업은 다음 배치로 분리한다.
- 다음 경우에는 10건 전에 조기 체크포인트를 허용한다.
  - `HIGH_RISK_CONFLICT`
  - `SESSION_END`
  - `LARGE_CANON_IMPACT`

체크포인트에는 Decision ID, 권위 파일, exact head 또는 merge SHA, 검증 상태, 미해결 위험, 다음 Gate를 기록한다.

## 2. 항상 TDD

모든 작업은 다음 순서를 따른다.

```text
RED
→ GREEN
→ REFACTOR
→ exact-head verification
```

- 구현 전에 관련 실패를 재현하는 테스트가 있어야 한다.
- 문서·정본·정책 작업도 예외가 아니다. 실행 코드가 없으면 실패하는 contract·schema·regression 검사를 먼저 만든다.
- 무관한 실패를 RED 증거로 사용하지 않는다.
- 검증되지 않은 상태를 완료로 주장하지 않는다.

## 3. 벤치마킹과 현업 비교

**모든 프로젝트 작업**은 작업 시작 전에 벤치마킹과 현업 조사를 먼저 수행한다. 조사 깊이는 작업의 위험·범위에 비례시키되 선행 단계 자체는 생략하지 않는다.

게임 기획·시스템·밸런스·UX/UI·구현 구조·작업 방식·도구 선택처럼 실질적인 질문과 작업에서는 현재안 또는 제안안을 외부 사례와 본격 비교한다.

벤치마킹과 현업 조사는 **계획·권장안 확정·파일 수정·코드/문서 mutation보다 먼저** 수행한다. 실질 작업의 기본 순서는 다음과 같다.

```text
Base·프로젝트 GitHub·Sheet current authority fresh-read
→ 벤치마킹·현업 조사
→ 프로젝트 코어 기준 적합성/차이/권장안 정리
→ 계획·TDD RED·수정 작업
```

작업 시작 전 research packet에는 최소 다음을 남긴다.

- 현재 project authority와 비교할 외부 질문.
- 사용한 공식/1차/신뢰 가능한 비교 출처.
- 프로젝트안과 비교 사례의 공통점·차이.
- 그대로 복사하면 안 되는 맥락 차이.
- 프로젝트 코어를 기준으로 한 권장 방향.

권장 출처 순서:

1. 공식 문서·표준.
2. 1차 연구·제작사 기술 문서.
3. 제작사 사례 연구·포스트모템.
4. 신뢰할 만한 2차 종합 자료.

가능하면 신뢰 가능한 비교 대상 두 개 이상을 사용하고 다음을 제공한다.

- 프로젝트안과 업계 사례의 공통점·차이.
- 그대로 채택하면 안 되는 맥락 차이.
- 프로젝트 코어를 기준으로 한 권장안.

신뢰 가능한 비교 대상을 찾지 못하면 사례를 만들어내지 않고, 자료 공백과 내부 가정을 명시한다. 벤치마킹은 프로젝트 코어를 대체하지 않으며 복사 근거가 아니라 선택 검증 도구다.

## 4. 적대적 검토

각 작업은 최소 다음을 검사한다.

- 핵심 재미 적합성.
- 정본·Decision 충돌.
- 기획 누락.
- 악용·어뷰징 경로.
- 구형 참조 drift.
- 실행하지 않은 검증의 과장.
