# 십보강호 UI·UX·사운드 에셋 파이프라인 설계

> 상태: `USER_APPROVED_PROCESS / REVIEW_IN_PROGRESS`  
> 적용 범위: PoC 주요 비무 1~5의 UI·UX·전투 연출·사운드  
> 제품 런타임·실제 에셋 취득·생성: `NOT_STARTED`

## 1. 목적

십보강호의 UI·UX·사운드는 에셋을 먼저 확보한 뒤 게임을 그 에셋에 맞추지 않는다. 먼저 전투 정보 구조와 무협·수묵 컨셉에 필요한 표현을 정의하고, 현재 사용할 수 있는 에셋을 조사한 뒤, 부족한 항목만 생성하거나 보정한다.

최종 순서는 다음과 같다.

```text
컨셉·정보 요구 정의
→ 필요한 자산 목록과 gap map 작성
→ 에셋 스토어·라이브러리 최신 검색
→ 라이선스·스타일·Godot 적합성 평가
→ 채택 / 보정 / 생성 / 보류 판정
→ 부족분만 생성
→ Godot 통합
→ 가독성·접근성·사운드 피로·성능 검증
```

## 2. 단계 1 — 컨셉과 기능 요구

### UI·UX

- 수묵 기반 무협 분위기를 유지하되 판독성을 우선한다.
- 화려함보다 위치·거리·3/3/4 슬롯·타격쌍·합·중단·필중·성장 원인을 읽게 한다.
- 색·이미지·모션이 없어도 도형·텍스트·로그로 핵심 정보를 전달한다.
- 기본 절초, 10성 절초, 성장 보상, 유료 재도전을 같은 정보 위계 안에서 설명한다.

### 사운드

- 사운드는 분위기와 사건 강조를 담당하되 단독 정보 채널로 사용하지 않는다.
- 전조, 합, 방어, 회피, 체력 피해, 중단, 강건, 필중 소비, 절초, 보상, 재도전 등 사건별 cue 요구를 먼저 작성한다.
- 다타격에서 소리가 겹쳐 판정 순서를 가리지 않도록 우선순위와 동시 재생 제한을 설계한다.
- 음소거·모션 감소·즉시 완료에서도 텍스트와 시각 정보가 동일 결과를 제공한다.

## 3. 단계 2 — 에셋 필요 목록과 gap map

화면·사건별로 다음 상태를 기록한다.

- `EXISTING_ACCEPT`: 기존 자산을 그대로 사용.
- `EXISTING_ADAPT`: 크롭·색조·루프·노이즈 정리 등 보정 후 사용.
- `STORE_CANDIDATE`: 외부 에셋 후보를 검색.
- `GENERATE_REQUIRED`: 적합한 외부 후보가 없어 생성 필요.
- `DEFER`: PoC 핵심 전달과 무관해 보류.

자산 단위는 최소한 다음을 포함한다.

- HUD·패널·버튼·카드·상태 아이콘·전장 타일·포커스 표시.
- 합·중단·필중·절초·보상·재도전의 VFX 또는 모션.
- UI 확인·취소·경고·선택·결제 cue.
- 공격·합·방어·회피·체력 피해·중단·강건·필중·절초 cue.
- 전투·지도·결과 화면의 ambience와 BGM 후보.

## 4. 단계 3 — 에셋 스토어 검색과 평가

실제 검색 시점의 최신 에셋 스토어·라이브러리·제작 도구를 사용한다. 후보마다 다음을 기록한다.

1. 출처 URL과 취득일.
2. 제작자와 에셋 버전.
3. 무료·유료 여부와 가격.
4. 상업 이용·수정·재배포·표기 조건.
5. Godot 4 import 가능 형식과 필요한 변환.
6. 해상도·벡터 여부·루프 가능 여부·샘플레이트.
7. 수묵 무협 컨셉 적합성.
8. 다른 자산과의 일관성.
9. 접근성·가독성·사운드 피로 위험.
10. 성능·파일 크기·동시 재생 비용.

라이선스가 불명확하거나 원본 출처를 확인할 수 없는 자산은 사용하지 않는다. 에셋 검색 결과는 기능 적합성보다 먼저 구매 여부를 결정하는 근거로 사용하지 않는다.

## 5. 단계 4 — 채택 판정

각 후보는 다음 중 하나로 판정한다.

- `ADOPT`: 수정 없이 채택.
- `ADAPT`: 라이선스가 허용하는 범위에서 보정 후 채택.
- `GENERATE`: 필요한 기능·스타일·법적 조건을 만족하는 후보가 없어 생성.
- `REJECT`: 라이선스·스타일·성능·접근성 문제로 제외.
- `DEFER`: PoC 성공 조건과 무관해 보류.

동일 기능에 여러 후보가 있으면 컨셉 적합성보다 **정보 전달과 라이선스 명확성**을 먼저 비교하고, 그다음 제작 비용과 스타일 일관성을 비교한다.

## 6. 단계 5 — 부족분 생성

생성은 에셋 검색과 gap 판정 뒤에만 수행한다.

- 기존 후보를 단순히 다시 만드는 중복 생성은 금지한다.
- 생성 전 크기·비율·상태 변화·루프·파일 형식·투명 배경·음향 길이 등 납품 규격을 정의한다.
- 생성 프롬프트·원본·편집본·변형본과 사용 도구를 기록한다.
- 생성 결과도 외부 에셋과 같은 가독성·성능·접근성 검사를 통과해야 한다.
- 사람·상표·저작물 모방이나 출처 불명 스타일 복제에 의존하지 않는다.

## 7. 단계 6 — 통합

- Godot import 설정과 원본 파일을 분리한다.
- UI 컴포넌트는 에셋 교체가 규칙 로직을 바꾸지 않도록 구성한다.
- 사운드는 사건 ID와 audio bus를 통해 연결하고 판정 엔진과 분리한다.
- 에셋이 누락되면 텍스트·도형·무음 폴백으로 기능을 유지한다.
- 외부 에셋·보정본·생성본의 출처와 적용 위치를 자산 원장에 연결한다.

## 8. 단계 7 — 검증

### UI·UX

- 첫 화면에서 위치·거리·자원·현재 묶음·진행 가능 이유를 찾을 수 있는가.
- 다타격 합과 중단 원인을 로그 재계산 없이 설명할 수 있는가.
- 색상 없이 상태와 선택 가능 여부를 구분할 수 있는가.
- 키보드·포커스·모션 감소·즉시 완료에서 기능이 동일한가.

### 사운드

- 사운드를 꺼도 모든 핵심 사건을 이해할 수 있는가.
- 다타격·합·효과음이 겹쳐 사건 순서를 숨기지 않는가.
- 반복 전투에서 경고음·타격음·UI음이 피로를 유발하지 않는가.
- BGM과 SFX가 로그·대사·중요 cue를 가리지 않는가.

### 상태 경계

실제 스토어 조사, 에셋 취득, 생성, Godot 통합, 접근성 사용자 테스트와 사운드 선호 검증은 아직 `NOT_RUN / BLOCKED_UNVERIFIED`다.

## 9. 구현 인계 경계

`검수 완료` 뒤 Codex 인계는 다음 순서를 따른다.

1. UI·UX·사운드 event matrix와 asset gap map 작성.
2. 최신 에셋 스토어 검색과 라이선스 원장 작성.
3. 후보 비교와 채택 판정.
4. 부족분 생성 명세와 제작.
5. Godot 통합.
6. 자동·접근성·성능·사람 검증.

이 순서를 거치지 않은 임의 에셋 선택이나 구현자 취향 기반 생성은 승인 범위가 아니다.
